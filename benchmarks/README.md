# Бенчмарк LLM-этапов gMART

Поэтапный бенчмарк «вызов → результат» для подбора модели (или связки моделей) под
мультиагентную систему. Каждый кейс прогоняет **один LLM-этап агента** на настоящем
коде gMART — тех же prompt-builders, JSON-схемах и парсерах, что в проде, — но без
Urban API, MCP, Redis и ChatStorage: на вход подаются зафиксированные данные, на выходе
проверяется структурированный ответ модели.

- **auto-этапы** (планы, маршрутизация, маппинги, критики) оцениваются детерминированно:
  проверки сравнивают поля ответа с эталоном.
- **manual-этапы** (ответы пользователю, сводки, названия) получают формальные проверки
  (числа, источники, запреты), а их тексты складываются в `review.md` для оценки глазами.

## Быстрый старт

```bash
cp benchmarks/config.example.yaml benchmarks/config.yaml   # адреса моделей; файл в .gitignore
uv run python -m benchmarks list                            # этапы и число кейсов
uv run python -m benchmarks run --config benchmarks/config.yaml --tags smoke
uv run python -m benchmarks run --config benchmarks/config.yaml --models qwen27b,gptoss20b
uv run python -m benchmarks run --config benchmarks/config.yaml --profiles mixed --stages "orchestrator.*,provision.*"
```

Опции `run`: `--profiles`, `--models` (по профилю «одна модель на всё» на каждую),
`--stages` / `--cases` (glob), `--tags`, `--repeat`, `--concurrency`, `--save-prompts`
(сохранять промпты и схемы в результаты), `--label`, `--out`, `--case-timeout`.

## Конфигурация моделей

`config.yaml` описывает три уровня:

- `endpoints` — серверы: `backend: openai` (vLLM и любой OpenAI-совместимый) или
  `ollama`; для OpenAI — `think_mode` (`reasoning_effort` | `chat_template` | `off`),
  `think_effort`, `think_chat_template_kwarg` — как в `OPENAI_THINK_*` агентов.
  Политика адресов gMART действует и здесь (запрещённые хосты отклоняются).
- `models` — именованная пара «эндпоинт + id модели» и `options`, которые добавляются
  к каждому вызову.
- `profiles` — что сравнивается: `default` для всех этапов и `stages` с
  переопределениями по id или glob (`"scenario.*": qwen14b`). Так меряется матрица
  этап × модель и проверяются связки «большая модель на планирование, малая на
  маппинги».

`${VAR}` / `${VAR:-default}` в конфиге подставляются из окружения — ключи в файл не пишем.

## Результаты

`benchmarks/results/<время>-<label>/`:

| Файл | Что внутри |
|---|---|
| `report.md` | итог по профилям, лучший профиль на каждом этапе, матрица этап × профиль (pass rate, балл, стабильность, латентность ср/p95, токены, число вызовов), все проваленные проверки с ожидаемым и полученным |
| `results.jsonl` | запись на каждый прогон: вход, выход, проверки, сырые ответы модели (`calls`), латентность, токены |
| `review.md` | ответы manual-этапов бок о бок по профилям, с подсказкой, что проверить |
| `grades.csv` | шаблон ручных оценок 0–2; после заполнения `python -m benchmarks report <каталог>` включает их в отчёт |
| `summary.json`, `meta.json` | то же в машинном виде и параметры прогона |

Профили выполняются последовательно (чтобы латентность одной модели не искажалась
другой), кейсы внутри профиля — с `concurrency`. `--repeat N` показывает
стабильность: долю кейсов с одинаковым исходом во всех повторах.

## Что измеряет каждый этап

`python -m benchmarks list` выводит этапы. Важное про охват:

- Если код агента после модели исправляет план детерминированно (канонические
  названия, дополнение шагов), выход содержит **сырой план модели** на верхнем уровне и
  итог пайплайна в `final`. Проверка `mode` оценивает модель, `final.mode` — то, что
  выполнит агент.
- Повторные запросы при невалидном JSON (repair-ретраи) — часть этапа, как в проде:
  `Вызовов` > 1 в отчёте значит, что модель ошибалась в формате.
- Кодовые короткие пути, которые обходят модель (точное совпадение названия, алиас
  колонки, «да/нет»), в кейсах не используются; где они возможны, выход содержит
  `llm_called`.
- Критики вызываются без кодовых предпроверок, которые им предшествуют в проде
  (`ungrounded_quantities`, `deterministic_checks`), чтобы оценить саму модель.

Не покрыты в этой версии: `dvd.answer`/`dvd.critic`/`dvd.revision`/`dvd.context_reducer`,
`scenario.plan`, `provision.answer`, `restriction.answer`, `pzz.answer`,
`context_summary` — у них большой динамический контекст. Их можно сравнивать через этап
`chat`: положите в кейс `messages` из лога gMART (снимок промпта).

## Как добавить кейс

Файлы `cases/*.yaml`; ключ `stage` задаётся на файл или на кейс, `defaults`
подмешиваются под `input` каждого кейса, якоря YAML (`&name` / `*name`) — для общих
каталогов и контекстов.

```yaml
- id: followup_population_from_history
  stage: provision.plan
  tags: [history]
  input:
    services_catalog: ["Школа", "Детский сад"]
    history:
      - {role: user, content: "Какая обеспеченность школами?"}
      - {role: assistant, content: "Обеспеченность школами — 78%."}
    user_query: "Пересчитай с населением 30000"
  expect:
    - {path: mode, eq: provision}
    - {path: final.service_name, eq: "Школа"}
    - {path: target_population, eq: 30000}
  review: "что посмотреть глазами (для manual-этапов)"
```

Проверка — `path` в выходе и ровно один оператор:

| Оператор | Смысл |
|---|---|
| `eq`, `ne` | равенство (строки без учёта регистра, `ё`/`е` и лишних пробелов; списки — по порядку) |
| `in`, `not_in` | значение из списка |
| `set_eq` | список равен множеству (порядок не важен) |
| `contains`, `not_contains`, `contains_any` | подстроки в строке или элементы в списке |
| `subset` | все элементы списка из разрешённых |
| `len`, `min_len`, `max_len` | длина списка или строки |
| `null` | `true` — пусто/нет поля, `false` — заполнено (ключ пишите в кавычках: `"null"`) |
| `regex`, `not_regex` | регулярное выражение по строке |
| `approx` (+`tol`), `gte`, `lte` | числа |

Путь: `steps.0.agent`, `steps[*].agent` (поле по всему списку), `by_topic.жилой дом`.
`weight` меняет вес проверки в балле кейса, `name` — подпись в отчёте. Кейс пройден,
если пройдены все проверки; балл — взвешенная доля пройденных.

Новый этап — функция с декоратором `@stage(...)` в `benchmarks/stages/*.py`, которая
вызывает код gMART с `ctx.llm` и возвращает JSON-совместимый результат.

Тесты харнесса: `uv run pytest tests/unit/test_benchmark_harness.py`.
