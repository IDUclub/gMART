# Первый этап аналитического оркестратора

Сложный запрос по умолчанию проходит цикл «цель и условия готовности → одно действие
→ специализированный расчёт → проверка доказательств → следующее действие или итог».
Обязательный подробный план не нужен. Исходные требования сохраняются независимо
от решений модели; модель не может удалить их при выборе следующего действия.
Оркестратор сравнивает результаты; специалисты получают отдельные задачи.

`ORCHESTRATOR_ANALYSIS_MODE=goal` включает этот режим (значение по умолчанию).
`plan` оставлен для сравнения с прежней реализацией. В режиме `goal` запрос сразу
переходит к выделению цели независимо от формулировки. Если сама задача не определена,
модель возвращает конкретный вопрос через `clarification_question`; отсутствие
данных или нормативов предварительно не предполагается.

Выделение требований использует `ORCHESTRATOR_GOAL_REASONING_EFFORT=medium`;
выбор аналитического действия и итоговая оценка используют `high` с ограниченной
повторной попыткой на `medium`. На удалённом gpt-oss высокий reasoning уже приводил
к исчерпанию генерации до выдачи JSON даже при выделении требований.

## Условия готовности

Каждое требование содержит ID, исходную цитату запроса, описание результата,
специалиста, сценарий и обязательные типы артефактов. Для типизированной выборки
фиксируются также вид сущности (услуги или физические объекты) и один тип объекта.
При выделении цели модель указывает ID пронумерованных фрагментов запроса;
исходные цитаты подставляет приложение. Дословное воспроизведение текста моделью
не требуется, неизвестные ссылки отклоняются с ограниченным исправлением.
Модель выбирает `requirement_id` и одно действие; приложение привязывает его к
сохранённому сценарию и специалисту. Вспомогательное исследование (`support=true`)
может получить дополнительные данные, но само по себе не закрывает расчёт.

Состояние `satisfied` вычисляется по подтверждённым артефактам выполненного действия.
Неполные таблицы, слои другого типа, разные идентификаторы объектов или число
строк/геометрий не закрывают условие. Пустая таблица не подтверждает расчёт
обеспеченности; пустая полная выборка объектов корректно подтверждает нулевое количество. Ложный `complete`
от модели отклоняется с ограниченным исправлением управляющего ответа.
Сбой отдельного требования оставляет доступными независимые результаты.
Причина блокировки сохраняется даже при последующей ошибке модели.
По полным выборкам приложение формирует таблицу количества и разностей с первой
строкой того же вида сущности; эта таблица и текстовый подсчёт доступны также при
заблокированном расчёте. Числа берутся из сохранённых строк, не из ответа модели.

`orchestrator_final.goal` содержит цель и состояние каждого требования:
`pending`, `satisfied` или `blocked`, ссылки на доказательства и причину остановки.
Цель, попытки и полные артефакты сохраняются вместе с аналитическим контекстом.
При `continue_from` продолжается та же цель: успешные результаты сохраняются,
заблокированные действия можно повторить после восстановления данных/сервиса.
Для новой задачи или изменённых критериев используйте новый запрос в том же чате
без `continue_from`; предыдущие доказательства остаются доступны в контексте.

Полнота извлечения требований из произвольного естественного языка и содержательная
правильность выводов всё ещё зависят от модели. Проверка схемы и происхождения
артефактов не доказывает причинность или правильность любой интерпретации запроса.
Эти свойства проверяются отдельными повторными интеграционными сценариями.

## Поддерживаемые сценарии

| Цель | Поведение | Проверка |
| --- | --- | --- |
| Базовый сценарий и два варианта | Отдельные scenario_id, пересмотр оставшегося плана, таблицы исходных значений, разностей и процентов со ссылками на строки | `test_compare_three_scenarios_replans_and_returns_full_artifacts` |
| Почему показатель ухудшился | Проверка исходных данных и методики; подтверждения отделены от гипотез; при нехватке сведений конкретный вопрос | `test_unexpected_result_separates_hypothesis_and_requests_missing_inputs` |
| Продолжение с новыми условиями | Подтверждённые артефакты сохраняются; перед новой работой пересматривается только оставшийся план. Относительное население вычисляется из ссылки на таблицу и множителя | `test_changed_assumptions_reuse_confirmed_context_without_rerunning_base` |
| Ограниченный бюджет или недоступные данные | Остановка повторяющегося шага, общий бюджет, сохранение результатов, объяснение недостающего | Тесты времени, повторов, пустого нормативного корпуса и ошибок в `test_analytical_orchestrator.py` |

Эти проверки проверяют поведение оркестратора с контролируемыми границами сервисов.
Они не подтверждают наличие данных во внешних системах или качество любого
произвольного аналитического ответа модели.

## Общий бюджет

Настройки передаются через окружение; они также подключены к compose и workflow.
Лимиты относятся ко всему запросу, включая вложенных агентов и повторные обращения.

| Переменная | По умолчанию |
| --- | ---: |
| `ORCHESTRATOR_TOTAL_TOKENS` | 400000 |
| `ORCHESTRATOR_MODEL_CALLS` | 60 |
| `ORCHESTRATOR_TOOL_CALLS` | 80 |
| `ORCHESTRATOR_SECONDS` | 600 |
| `ORCHESTRATOR_STEPS` | 12 |
| `ORCHESTRATOR_CONTEXT_TOKENS` | 32768 |
| `ORCHESTRATOR_OUTPUT_TOKENS` | 16384 |

Перед обращением к модели резервируются вход и максимально допустимый выход.
После ответа резерв заменяется фактическим `usage`, включая reasoning tokens.
Если сервер не сообщает расход или обращение оборвалось, резерв остаётся списанным,
а `estimated_calls` увеличивается. Оценка входа по UTF-8 консервативна для используемых
byte-based токенизаторов и включает запас на оформление. Контекст сервера должен
соответствовать настройкам приложения. Автоматические HTTP-повторы клиента OpenAI
внутри бюджетного запуска отключены; явные повторы JSON учитываются отдельно.

Для итоговой проверки резервируются 16384 токена и один вызов модели. При нехватке
ресурса всегда доступен ответ приложения без дополнительного LLM-вызова.
Объём выборок контекста уменьшается с доступным бюджетом; весь исходный запрос
сохраняется. Если обязательный контекст не помещается, оркестратор объясняет остановку.

`high` может значительно увеличить время и расход. Для аналитических JSON-решений
схема передаётся в запросе, а SDK проверяет ответ и выполняет ограниченное исправление.
Это обходит наблюдавшееся на dev Harmony-сервере исчерпание генерации при ограничении
декодера JSON-схемой, сохраняя проверку структуры результата.
Если ответ оборван или не проходит проверку, ограниченная повторная попытка использует
`medium`. Она работает с теми же исходными данными и учитывается в `reasoning_fallbacks`.
Это восстановление управляющего ответа, а не повышение уверенности в выводах.

## Контекст и артефакты

Полные таблицы, GeoJSON, текстовые ответы и результаты нормативных проверок хранятся
отдельно от выборок для модели. Каталог содержит ID, тип, происхождение и подтверждённость.
Модель может читать страницы через `inspect`; `_catalog` открывает страницы каталога.
У частичных таблиц сохраняются `complete=false` и исходное число строк.
Результат незавершённого шага не допускается в качестве доказательства.

Разности и проценты вычисляются приложением через Decimal по точным ссылкам
`artifact_id/row/column`. Несуществующие ссылки, ненумерические значения и конфликтующие
известные единицы, годы, территории или методики отклоняются. Если этих метаданных нет,
содержательную сопоставимость всё ещё оценивает модель; это не универсальная
автоматическая проверка причинности или научной корректности.

Слои и таблицы передаются в `step_event`. `orchestrator_final` содержит:

- `status`: `completed` или `blocked`, независимо от успеха отдельных шагов;
- `answer`, `hypotheses`, `evidence_ids`;
- `missing`: чего не хватает, зачем, вопрос, пример ответа, `owner=user/service/budget`;
- `artifacts`: полный каталог с признаком `confirmed`;
- `budget`: лимиты и фактический/оценочный расход;
- `continue_from`: ID для продолжения в новом запуске.

Frontend показывает итоговый ответ, помечает неподтверждённые результаты и восстанавливает
сохранённые слои без повторного выполнения инструментов. При включённой истории
подтверждённые артефакты и контекст сохраняются в ChatStorage. Ошибка записи истории
возвращается предупреждением; текущая выдача и Redis-контекст остаются доступны.

## Продолжение

`GET /orchestrator/route/stream` принимает дополнительные параметры:

- `continue_from=<request UUID>` — новый анализ с сохранёнными подтверждениями;
- `budget_tokens` и `budget_seconds` — уменьшение серверного лимита для этого запроса.

Новый запрос с прежним `chat_id` также использует сохранённый аналитический контекст.
Сначала проверяются существующие результаты; повторно выполнять базовые расчёты
ради восстановления истории не требуется. Изменение условий задаётся новым текстом.
Геометрия хранится полностью, но произвольные вычисления над любым сохранённым слоем
зависят от интерфейсов специализированных инструментов.

`request_id` сохраняет прежнее значение: повторная выдача буфера без модели и MCP.
Redis-контекст анализа хранится 24 часа отдельно от 15-минутного буфера SSE и изолирован
по субъекту токена. Для чата возможна загрузка снимка из доступной истории ChatStorage.
Если снимок недоступен, приложение явно просит восстановить исходные условия.

В dev ранее обнаружены пустой нормативный корпус и ошибка ObjectEffects при отсутствии
нормативных данных. Код оркестратора не создаёт отсутствующие нормы: такие задачи должны
заканчиваться объяснением неполноты, а не вымышленным успешным расчётом.

## Проверка с dev-моделью 12 сентября 2026

Полный синтетический прогон через реальный SDK и `gpt-oss-20b` завершился за 57,58 с:
два специализированных шага, пересмотр плана, три таблицы (включая вычисленное
сравнение), два пустых тестовых слоя, итоговый ответ, проверка SSE-схемы и точный replay.
Расход: 22921 токен, четыре обращения к модели, один переход к `medium` при восстановлении.
Границы MCP и Redis в этом прогоне были локальными тестовыми реализациями.
Отдельный прогон с лимитом 240 с остановился и сохранил обе таблицы и оба слоя.

Повторяемый live-model тест: `tests/integration/test_analytical_orchestrator_live.py`,
параметры `VLLM_BASE_URL` и `VLLM_MODEL`. Без адреса тест пропускается. Все данные в нём
вымышлены. Unit-тесты отдельно проверяют точный расчёт, ошибки, изоляцию контекста,
параллельное сохранение, остановку и восстановление артефактов.

Dev MCP проверялся отдельно: получение количества школ прошло, но первые варианты
аналитического JSON завершались обрывом модели. Повторная диагностика с сохранёнными
dev-артефактами была отклонена автоматической проверкой доступа; исправление проверено
на синтетических данных. Полное успешное сравнение реальных dev-сценариев этим прогоном
не подтверждено.

## Контракты стабильности и доставки артефактов

В режиме цели типизированная выборка передаётся специалисту как `EntitySelection`,
без повторной классификации управляющего текста. Имена сверяются с фактическим
каталогом MCP. Дополнительные фильтры требуют общего workflow (`entity_kind=other`).
Одинаковые требования к таблице и слою объединяются с сохранением исходных цитат.
Запрошенные типы артефактов согласуются с контрактом специалиста.

Пустой каталог и повторное чтение неизменившегося среза не считаются прогрессом.
После ограниченного исправления решения приложение может выполнить оставшееся
независимое требование из неизменной цели. Оно не придумывает отсутствующие данные.
При продолжении исторические неудачные попытки не заменяют проверку в новом запросе.
Таблица количества материализуется до финального обзора, поэтому сравнение может
ссылаться на реальные числовые ячейки.

Bearer JWT проверяется по подписи, issuer и сроку действия перед использованием
субъекта. Replay привязан к владельцу; request ID атомарно резервируется одной
попыткой. Контекст записывается в Redis hash по идентификаторам артефактов и шагов,
без конфликтующей перезаписи полного JSON. Старый JSON-контекст читается при миграции.

DVD и NormGraph передают `source_evidence` с исходными записями, а не сгенерированными
моделью URL. Оркестратор сохраняет записи и добавляет ссылки на защищённые снимки:
`GET /orchestrator/runs/{request_id}/artifacts/{artifact_id}`. `PUBLIC_AGENTS_URL`
задаёт внешний origin; без него используются относительные ссылки. Снимки доступны
в течение срока хранения контекста (24 часа), полное содержимое также находится в
ChatStorage. Это снимки использованных источников с исходными ID и версиями, а не
обещание актуальности нормативной базы после момента анализа.

В интерфейсе блокированный анализ предлагает явное продолжение с `continue_from`.
Кнопка привязана к чату и сценарию, а якорь восстанавливается из истории. Повторная
выдача сохраняет `artifact_id`; таблицы и слои не дублируются при восстановлении.
Полная матрица и команды запуска: `tests/integration/local_stack/README.md`.
