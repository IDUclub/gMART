# Аудит данных для исполняемых норм

Аудит выполнен 20 августа 2026 года на тестовом контуре Urban API
`https://urban-api.testing.idulab.ru/api`. Его цель — зафиксировать, какие шаблоны
можно проверять на реальных данных без догадок модели. Числа являются снимком
контура на дату аудита и не считаются неизменяемой версией данных.

## Проверенные сценарии

| Сценарий | Проект | Физические объекты | Сервисы | Источники функциональных зон |
| --- | ---: | ---: | ---: | --- |
| 772 | 604 | 21 | 24 | PZZ 2023, OSM 2024 |
| 744 | 593 | — | — | OSM 2025 |
| 1429 | 938 | 27 | 52 | OSM 2024 |
| 198 | 120 | — | — | PZZ 2023, OSM 2024, User 2026 |

Эталонные выборки:

- сценарий 772: 70 полигонов жилых домов, 3 точечных объекта школ;
- сценарий 744: 1 полигон промышленного объекта;
- функциональные зоны: 124 PZZ и 100 OSM в сценарии 772, 7 OSM в сценарии 744,
  68 пользовательских зон в сценарии 198.

## Атрибуты и качество

Для 70 жилых домов сценария 772 получены следующие заполненности:

| Кандидат роли `floors` | Заполнено | Fill-rate | Тип/качество |
| --- | ---: | ---: | --- |
| `building.floors` | 59 | 0,843 | число, direct |
| `building.properties.floor_count_min` | 59 | 0,843 | число, direct |
| `building.properties.storeys_count` | 50 | 0,714 | число, direct |
| `osm.building:levels` | 65 | 0,929 | строка, требует нормализации |
| `osm.height` | 2 | 0,029 | высота, допустима только через `height_to_floors_v1` |

У трёх школ атрибут вместимости заполнен у всех трёх объектов. Функциональные
зоны содержат идентификаторы, типы и геометрию, но в проверенных ответах нет
универсального нормативного порога или коэффициента застройки.

Зарегистрированное преобразование `height_to_floors_v1` использует
`max(1, floor(height_m / 3))`. Оно применяется только тогда, когда CheckPlan явно
разрешает соответствующий derived-кандидат; свободные выражения не исполняются.

## Решение по шаблонам

| Шаблон | Решение | Основание |
| --- | --- | --- |
| `distance_from_source@v1` | включён | есть точечные и полигональные генераторы и цели |
| `distance_table@v1` | включён | есть числовые атрибуты с измеримым fill-rate; пропуски остаются unchecked |
| `presence_within@v1` | включён | есть объекты и соседи, полный anti-join выполняется детерминированно |
| `zonal_attribute_threshold@v1`, constant | включён | геометрия зон и константный порог приходят раздельно |
| `zonal_attribute_threshold@v1`, attribute role | контракт включён, данные обычно `unverifiable` | пороговый атрибут зон не подтверждён |
| `zonal_ratio@v1` | включён | зоны и полигональный числитель доступны; расчёт идёт в локальной метрической CRS |

## Ограничения и воспроизводимость

- Пустой результат классифицируется как `not_applicable` только для полной,
  нетранкированной выдачи. Ошибка Urban API не превращается в пустой слой.
- Значения, которые не удалось привести к числу, уменьшают покрытие; они не
  заменяются средним или типовым значением.
- Повтор MCP-вызовов из ChatStorage является новым расчётом по текущему сценарию.
  Для точного исторического воспроизведения нужен неизменяемый revision либо
  снимок исходных слоёв.
- Машиночитаемая матрица сценариев находится в
  `tests/fixtures/compliance/data_audit_scenarios.json` и не содержит токенов или
  иных секретов.

## Как повторить аудит

1. Получить сервисный пользовательский токен тестового контура, не сохраняя его
   в репозитории.
2. Запросить каталог сценария, физические объекты, сервисы и функциональные зоны.
3. Проверить число features, полноту пагинации, типы геометрии и fill-rate путей
   из матрицы fixture.
4. Сравнить результат с таблицами выше и обновить дату/матрицу, если схема или
   наполнение тестового контура изменились.
