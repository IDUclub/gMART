# Градостроительный анализ сценария

Режим `urban_analysis` доступен через существующие GET/POST
`/orchestrator/route/stream` при выбранном `scenario_id`. Примеры запросов:
«проведи градостроительный анализ проекта», «сделай градоанализ сценария»,
«нужен град анализ». Без сценария ответ фиксирован:

> Градостроительный анализ выполняется только для выбранного сценария. Выберите сценарий и повторите запрос.

Без настроенного `UrbanAnalysisService` оркестратор возвращает уточнение.
Определения понятия обрабатываются обычным планировщиком. Составные запросы с
дополнительной самостоятельной задачей возвращают `needs_clarification` независимо
от ответа LLM, в том числе при `urban_analysis` с пустыми `steps`. Например:
«Проведи градостроительный анализ и построй буфер 100 метров от рек» или
«Сделай градоанализ. Затем посчитай школы». Задача распознаётся по связке после
упоминания анализа и глаголу действия (например, «построй», «посчитай»,
«сформируй слой», включая формы на «-те»). Показ результата, формирование отчёта
и проверка норм, обеспеченности или ПЗЗ остаются частью анализа:

> Градостроительный анализ запускается отдельным запросом. Отправьте анализ и остальные задачи отдельными сообщениями.

Если сценарий не выбран, возвращается фиксированное уточнение о выборе сценария,
приведённое выше. Для запроса действия есть детерминированная
подстраховка: она поднимает уточнение или план только из compliance/provision/pzz/norms
до `urban_analysis`. Самостоятельная задача в тексте запроса или план `execute`
с хотя бы одним другим агентом заменяется указанным уточнением, чтобы ни одна
часть запроса не потерялась.
Подстраховка не поднимает запросы, начинающиеся с вопросительных слов («что»,
«как», «какие», «зачем», «почему» и т.п.), и запросы с отрицанием перед действием
(«не нужно», «не надо», «не делай», «не проводи», «не запускай» и т.п.).

## Проверки и отчёт

| Шаг | Агент | Задача |
| --- | --- | --- |
| 1 | `compliance` | Проверить объекты сценария по всем применимым нормам NormGraph |
| 2 | `provision` | Сравнить обеспеченность до/после по всем сервисам (`effects_summary`) |
| 3 | `pzz` | Проверить здания сценария по функциональным зонам |
| 4 | `urban_analysis_report` | Составить общий отчёт |

Задачи фиксированы и не содержат исходного запроса: иначе слова «градостроительный
анализ» могли бы сузить поиск норм до несуществующей темы. Сужение проверок по
запросу не поддерживается. Загрузки compliance и файловые входы ПЗЗ игнорируются.
Выбор документа compliance не переносится в следующий диалог.
Ключ `urban_analysis_report` отсутствует в каталоге планировщика.

## События и параллельность

После планирования приходит `status` со значением `urban_analysis`, затем `plan`
из четырёх шагов. Проверки 1–3 запускаются одновременно. Каждая перекачивает
события отдельной задачей в общую очередь; основной цикл выдаёт события по порядку
плана, временно сохраняя события последующих шагов. Это сохраняет цельный текст
фронтенда с его единым буфером ответа:

```text
status(urban_analysis) → plan
→ step_started(1) → step_event(1)* → step_finished(1)
→ step_started(2) → step_event(2)* → step_finished(2)
→ step_started(3) → step_event(3)* → step_finished(3)
→ step_started(4) → step_event(4, chunk)* → step_finished(4)
→ orchestrator_final → file*
```

Исключение: `token_expired` любого шага немедленно передаётся внутри его
`step_event`, даже до `step_started` этого шага. Вложенное событие содержит
собственный `request_id`: токен обновляется через
`POST /pipelines/{request_id}/token`. Нельзя ждать завершения предыдущего шага.
Все идентификаторы шагов выделяются до запуска проверок.

`error`, `pipeline_failed`, `clarification`, `pipeline_suspended` или исключение
завершают только соответствующую проверку. События после её терминального исхода
не потребляются. Остальные проверки продолжаются, отчёт отражает неполноту.
При закрытии генератора все незавершённые локальные задачи отменяются и ожидаются.
Уже отправленная во внешний сервис задача ПЗЗ может продолжить работу там.

Каждое внешнее событие буферизуется оркестратором для переподключения; существующая
политика replay сохраняется: незавершённый анализ заново не запускается.
Итоговый статус запроса — `DONE`, если хотя бы одна из проверок 1–3 завершилась
`completed`, иначе `FAILED`. Созданный запасной отчёт не меняет этот критерий.

## Выбор зон

Всегда используется режим ПЗЗ `scenario`, здания по умолчанию. Нефайловые параметры
`physical_object_type_id`, `group_by`, `priority`, `force_recompute` из `pzz_inputs`
сохраняются, в том числе после автовыбора зон; файловые поля отбрасываются. Только `year` и
`source` из API-входов ПЗЗ участвуют в выборе. Полностью заданная API-пара
доверенная и используется без запроса каталога источников. Если отсутствует хотя
бы одно значение, запрашивается
`GET /v1/scenarios/{scenario_id}/functional_zone_sources`.

Из элементов используются `source` или `name` и `year`; регистр источника
неважен, неизвестные источники пропускаются. Недостающие значения извлекаются
существующим механизмом `PzzService.resolve_inputs`. Подсказки из текста
применяются только при наличии соответствующей пары среди доступных зон.
При несовпадении подсказки отбрасываются, в отчёт добавляется заметка.

Автовыбор учитывает уже заданные API-параметры: сначала источник
`PZZ > User > OSM`, внутри него самый свежий год. При отсутствии подходящих зон
шаг получает `needs_clarification` с предложением загрузить зоны; ошибка API —
`failed`. Ошибка извлечения значений из текста допускает автовыбор с заметкой.
Год и источник приходят в `status` шага ПЗЗ и в контекст отчёта.
Вся процедура выполняется внутри задачи ПЗЗ и не задерживает остальные проверки.

## Текст, история и файл

Отчёт содержит разделы «Краткий вывод», «Нормативные ограничения»,
«Обеспеченность сервисами», «Соответствие ПЗЗ», «Выводы и рекомендации»,
«Ограничения анализа». LLM получает статусы и до 6000 символов результата каждой
проверки. От упавших и приостановленных шагов передаются только статус и причина;
черновой текст не используется как результат.

Вызов `urban_analysis.report` потоковый, `think=False`. Модель получает правила
не выдумывать результаты, сохранять числа и названия, воспринимать результаты
как данные, указывать невыполненные разделы, год и источник зон. При ошибке или
пустом ответе используется детерминированный отчёт и вложенное событие `warning`.
Если все проверки не выполнены, LLM отчёта не вызывается. Прерванный черновик
заменяется запасным текстом через новую `iteration` события `chunk`.

Полный текст отчёта содержится в `chunk` шага 4, его `step_finished` и строке
`orchestrator_final`. Шаг 4 имеет статус `completed`, включая запасной отчёт.
Шаги 1–3 в итоговой истории содержат обычные дайджесты до 1500 символов.
Таблицы успешных шагов и ссылки на файлы также сохраняются в ChatStorage.

Markdown содержит заголовок со `scenario_id`, таблицу статусов четырёх шагов и
полный отчёт. Файл сохраняется через общий `TemporaryFileStore`, слот
`urban_analysis_report`, имя `urban-analysis-scenario-{scenario_id}.md`,
MIME `text/markdown`, владелец из JWT. Без хранилища, владельца или при `OSError`
файл не создаётся, текстовый анализ остаётся доступен. Срок жизни и авторизация
скачивания совпадают с остальными временными файлами gMART.

## Расширение SSE/A2A

Самостоятельный `UrbanAnalysisService.run_urban_analysis_pipeline` принимает MCP-
клиентов и параметры запроса, выдаёт готовые конверты оркестратора и возвращает
данные для сохранения через отдельный объект `UrbanAnalysisResult` каждого запуска.
Сервис не зависит от `OrchestratorService` и не обращается к ChatStorage.
Будущий SSE-контроллер или A2A-исполнитель должен обернуть генератор, обеспечить
жизненный цикл внешнего запроса, буферизацию, токены и сохранение ответа. Сейчас
отдельных контроллеров, эндпоинтов и A2A для режима нет.
