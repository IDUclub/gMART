# Агент городских данных

Агент `scenario-data-agent` отвечает на фактические вопросы по Urban API через
сгруппированный внешний Urban MCP. Он работает строго в режиме чтения и может
возвращать текст, таблицы и GeoJSON-слои.

## Контекст сценария

`scenario_id` необязателен:

- если он передан, агент использует общие и сценарные инструменты;
- если его нет, инструменты, где `scenario_id` является обязательным параметром,
  исключаются из каталога до планирования;
- если вопрос относится к конкретному сценарию, агент просит пользователя выбрать
  сценарий и не пытается угадать идентификатор.

Все шесть Urban MCP-групп загружаются с bearer-токеном пользователя. Загрузка
выполняется в режиме fail-fast: недоступность любой группы завершает запрос явной
ошибкой, чтобы агент не сформировал неполный ответ.

## Количество объектов по типам

Русскоязычные вопросы о количестве сущностей по типам обрабатываются
детерминированно, без вычислений LLM. Агент получает записи и типы сценария из
Urban MCP, исключает дубликаты и формирует текстовый итог и таблицу. Общий
справочник запрашивается только для ID, которого нет среди типов сценария:

- физические объекты считаются по уникальному `physical_object_id`;
- сервисы (услуги) считаются по уникальному `service_id`;
- можно запросить физические объекты, сервисы или оба набора;
- в таблицу входят все представленные в сценарии типы; типы с нулевым количеством
  не выводятся;
- если точное название типа не найдено, строка содержит исходный ID, явный статус
  и все найденные в близком разделе справочника варианты.

Слово «объекты» без уточнения неоднозначно. Вопрос вроде «Какие объекты есть в
сценарии и сколько их по типам?» завершает текущий запрос уточнением: физические
объекты, сервисы или оба набора. Ответ пользователя запускает новый запрос с тем же
`chat_id`; варианты «Физические», «Сервисы» и «И те и те» распознаются по истории.

Во время этой обработки клиент получает обычные события `status`: загрузка
каталога, получение данных, подсчёт и проверка результата. Отдельный heartbeat не
требуется — интерфейс должен обновлять показанный текст статуса при каждом этапе.

## Линейный plan-first workflow

Пилот включается флагом `SCENARIO_DATA_LINEAR_WORKFLOW_ENABLED`. При включении агент
сначала строит логический план, получает только необходимые актуальные справочники,
создаёт неизменяемую исполнимую ревизию и затем выполняет её строго последовательно.
После выполнения работает отдельная проверка полноты; нехватка данных создаёт новую
ревизию плана, а не изменяет уже исполнявшуюся. Ограничения: 10 вызовов Urban MCP,
20 workspace-операций, 3 перепланирования, 5 минут активной работы и 15 минут
абсолютного времени. Ожидание обновлённого токена не входит в активное время.

`SCENARIO_DATA_WORKSPACE_ENABLED` разрешает фиксированные операции над временными
DataFrame/GeoDataFrame-артефактами: описание, выборку, фильтр, выбор столбцов,
сортировку, дедупликацию, агрегацию, join справочника, пространственный фильтр и
выгрузку GeoJSON. Произвольные выражения, Python/SQL, URL и пользовательские пути
не поддерживаются. Payload хранится в tmpfs IDU MCP, а Redis содержит только
часовую метаинформацию и opaque handle, изолированный по пользователю и чату.

## REST/SSE

### `GET /scenario-data/qa/stream`

Параметры запроса:

| Параметр | Тип | Обязателен | Назначение |
|---|---|---|---|
| `request` | `string` | да | Вопрос пользователя |
| `model` | `string` | нет | Модель LLM |
| `temperature` | `number` | нет | Температура генерации |
| `scenario_id` | `integer` | нет | Контекст сценария Urban API |
| `chat_id` | `string` | нет | Продолжение истории ChatStorage |
| `request_id` | `string` | нет | Повтор буферизованных событий пайплайна |

Основные SSE-события: `pipeline_started`, `status`, `tool_call`,
`feature_collection`, `table`, `chunk`, `token_expired`, `pipeline_suspended` и
`error`. Линейный workflow дополнительно отправляет `plan_created`,
`plan_revision_created`, `mapping_started`, `mapping_completed`, `step_started`,
`step_completed`, `artifact_created`, `validation_started`, `validation_completed`,
`replanning`, `clarification_required` и `pipeline_failed`. Это проверяемая трасса
плана и статусов, а не внутренние рассуждения модели.

Явная остановка выполняется `POST /pipelines/{request_id}/cancel`. При истечении JWT
клиент получает `token_expired`, обновляет токен и в течение 60 секунд повторяет
`POST /pipelines/{request_id}/token`; пайплайн продолжает тот же шаг. Разрыв SSE не
останавливает серверное выполнение, а повторное подключение с `request_id` получает
буфер событий.

Значения `status.status`: `tool_discovery`, `planning`, `tool_execution`,
`response_analysis`, `answer_review`, `answer_retry`. Последние два относятся к проверке
ответа: `answer_review` — черновик оценивается, `answer_retry` — оценка отклонила его и
пайплайн идёт на второй проход за недостающими данными. Клиенту достаточно показать
`status.text`; список закрыт схемой `ScenarioDataStatus`, поэтому новый статус на стороне
сервиса требует и правки схемы.

Ответ приходит одним блоком событий `chunk` после проверки, а не по мере генерации:
черновик нужно оценить до показа пользователю. Формат событий при этом не изменился.

### `GET /scenario-data/indicators/stream`

Ручка «ответ по показателям»: то, что во фронтенде выбирается из меню «плюс» рядом с
полем ввода. Параметры запроса и SSE-контракт те же, что у `/scenario-data/qa/stream`,
отдельного поля режима нет — возможность выбирается URL.

Отличие одно: этот вход сразу ведёт в ветку показателей, минуя классификацию вопроса,
и по умолчанию сравнивает выбранный сценарий с базовым сценарием его проекта. Базовый
сценарий находится молча: агент читает сценарий, берёт его проект и его
`base_scenario`. Вопросов о базовом сценарии пользователю не задаётся никогда.

Пользователь знает сценарии по названиям, а не по ID, поэтому в тексте ответа сценарии
подписаны ролью и названием: «Ваш сценарий «…»» — выбранный в интерфейсе, «Базовый
сценарий «…»» — найденный базовый. Если выбран сам базовый сценарий, он подписан «Базовый
сценарий «…»». Если у сценария нет названия, вместо него выводится ID.

Ответ состоит из таблицы `scenario_analytics` и текста:

- **показатель не назван** («Сравни с базовым», «Что изменилось?», «Покажи показатели»,
  «Покажи все показатели») — в таблице все показатели уровня сценария, в тексте сводка;
- **показатель назван** («Покажи «Земли жилой застройки»», «Покажи численность населения»)
  — в таблице и тексте только он.

Таблица широкая, строка — один показатель. Ячейки значений, разницы и процента — числа, их
можно сортировать. Колонки:

| Ключ | Заголовок (`label`) | Значение |
|---|---|---|
| `indicator` | `Показатель` | название показателя |
| `unit` | `Ед.` | единица; для `%` — `% (разница — п. п.)`, при разных единицах — `км² / га`; `null` у безразмерных |
| `scenario_<id>` | подпись сценария | значение; `null`, если его нет |
| `difference` | `Разница` | ваш минус базовый; `null`, если не вычисляется |
| `change_percent` | `Изменение, %` | относительное изменение, 1 знак; `null` для `%` и базы 0 |

Без сравнения остаются только `indicator`, `unit` и одна колонка значений.

Сводка:

```
Сравниваются: базовый сценарий «Исходный пользовательский сценарий» → ваш сценарий «Сценарий от Рокета, вариант 1».

Показателей: в базовом — 44, в вашем — 37. Изменились — 8, без изменений — 29, нет значения в вашем — 7.

Изменения:
• Земли жилой застройки: 23,41 % → 97,6 % (+74,19 п. п.)
• Земли сельскохозяйственного назначения: 66,82 % → 0 % (-66,82 п. п.)
• Срок рекультивации территории: 34 175 → 8 366 дней (-75,5 %)
…

Нет значения в вашем сценарии: Средняя этажность, Численность населения, ….

Все значения — в таблице.
```

Изменения перечисляются по убыванию модуля относительного изменения, не больше 10; нулевые
разницы в текст не попадают. Расчёт плотности и вопросы «почему/источник» отвечают в
прежнем формате.

Сводка выдаётся всегда, даже когда сравнивать не с чем. В этом случае ответ
начинается с абзаца с причиной:

| Ситуация | Строка в ответе |
|---|---|
| Выбран сам базовый сценарий | `Этот сценарий — базовый сценарий проекта, сравнивать не с чем.` |
| У сценария не определён проект | `Проект сценария не определён, поэтому показана только сводка без сравнения.` |
| У проекта не задан базовый сценарий | `У проекта не задан базовый сценарий, поэтому показана только сводка без сравнения.` |
| Проект недоступен по правам | `Базовый сценарий недоступен, поэтому показана только сводка без сравнения.` |

Текст запроса решает, что именно вернуть: конкретный показатель («Покажи
«Численность населения»»), все показатели («Покажи все показатели») или расчёт
плотности. Сравнение отключается словами «без сравнения», «не сравнивай»,
«не надо сравнивать», «без базового», «только текущий сценарий», «только по этому
сценарию», «только мой сценарий» — тогда второй сценарий не запрашивается вовсе.

Если в запросе явно названы два и более сценария («сравни сценарии 772 и 848»),
базовый не подставляется: работает обычное сравнение по указанным ID.

На `/scenario-data/qa/stream` поведение не изменилось. Базовый сценарий там
подставляется только тогда, когда пользователь сам просит сравнение («сравни с
базовым», «чем мой сценарий отличается от базового»), но второй ID не назвал.

## A2A

### Обнаружение

```http
GET /scenario-data/.well-known/agent-card.json
```

Имя карточки: `scenario-data-agent`. Протокол: A2A 0.3.0, транспорт JSON-RPC.
Расширение `scenario-context/v1` объявлено в карточке как необязательное.

В карточке объявлены два скилла: `query-scenario-and-urban-data` и
`compare-scenario-indicators`. Это описание возможностей агента, а не маршрутизация:
запрос через A2A по-прежнему идёт в общий пайплайн, где ветка выбирается по тексту.
Сравнение с базовым сценарием по умолчанию доступно только через
`GET /scenario-data/indicators/stream`.

### JSON-RPC

```http
POST /scenario-data/a2a
Authorization: Bearer <token>
Content-Type: application/json
```

Поддерживаются методы `SendMessage`/`message/send`,
`SendStreamingMessage`/`message/stream`, `GetTask`/`tasks/get`,
`ListTasks`/`tasks/list`, `CancelTask`/`tasks/cancel` и
`GetExtendedAgentCard`.

`scenario_id` и `chat_id` можно передать через `params.message.metadata` или
DataPart. Для совместимости `scenario_id=772` также распознаётся в тексте.

```json
{
  "jsonrpc": "2.0",
  "id": "request-1",
  "method": "message/send",
  "params": {
    "message": {
      "role": "user",
      "parts": [{"kind": "text", "text": "Какие типы сервисов доступны?"}],
      "metadata": {"scenario_id": 772}
    }
  }
}
```

A2A-запуски выполняются с `persist_history=False`: они могут читать переданный
`chat_id` как контекст, но не создают и не изменяют историю ChatStorage.

Результаты преобразуются в артефакты:

- текст — `scenario-data-agent-text` (`text/plain`);
- GeoJSON — `geojson-<layer>` (`application/vnd.geo+json`);
- таблица — `table-<name>` (`application/json`).
