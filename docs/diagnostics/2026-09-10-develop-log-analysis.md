## 1. Redis: три ERROR утром 10 сентября

В строке 12 настроен адрес **gmart-redis:6379, база 0**. Учётные данные из URL здесь не воспроизводятся. Это внутреннее имя; оно не доказывает наличие опубликованного порта на сервере.

- 05:17:05.889, строка 714: `buffer_event → RPUSH` падает в фоновой задаче, `Task exception was never retrieved`.
- 05:17:07.325, строка 759: оркестратор не может завершить запрос, `set_status(DONE) → GET` падает.
- 05:17:56.187, строка 903: такой же сбой при завершении scenario_data.

Подтверждён обрыв уже используемого соединения при записи команды в сокет. Лог не устанавливает, кто закрыл соединение. Ошибки появляются после длительного перерыва в агентских запросах, что согласуется с устаревшими соединениями пула, но не доказывает эту причину. В 05:17:40 другой запрос оркестратора проходит без аналогичного ERROR: постоянная полная недоступность Redis также не доказана.

В локальном `src/agents/dependencies/init_dependencies.py:52` клиент создаётся через `from_url(..., decode_responses=True)`. Проверка установленного redis-py 8.1.0 с этой конфигурацией показала: retries=0, health_check_interval=0, socket_keepalive=True, socket_timeout=5. Версию и эффективные параметры в развёрнутом контейнере нужно сверить отдельно. Локальный вызов реального `PipelineStateStore.set_status` с имитацией Redis ConnectionError подтвердил распространение исключения после единственного GET; это воспроизведение обработки ошибки, а не причины сетевого обрыва.

Исправление:

1. Проверить перезапуски, OOM и логи Redis, DNS и соединение из контейнера agents. Если проблема инфраструктурная, устранить её прежде, чем маскировать повторными попытками.
2. Настроить проверку соединения перед использованием после простоя, например `health_check_interval=30`, и ограниченные повторы с backoff для безопасно повторяемых операций. Конкретные интервалы проверить на стенде. TCP keepalive в локальной версии уже включён.
3. Не включать безусловный повтор всех команд: после потери ответа `RPUSH` может добавить событие дважды. Для буфера нужны ID событий и дедупликация либо атомарная идемпотентная запись.
4. Исправить вызовы `_buf`, запускающие `asyncio.create_task(buffer_event(...))` без контроля результата: отслеживать задачи, забирать исключения, дожидаться записи критических событий. При недоступности хранилища возвращать явное состояние ошибки сохранения; не объявлять DONE, если фиксация не состоялась.
5. Проверить на реальном Redis сброс соединения между созданием состояния и завершением, а также потерю связи при записи буфера. Предыдущий прогон 300 запросов использовал fakeredis для состояния и такие сетевые сбои не покрывал.

Документация: [redis-py production usage](https://redis.io/docs/latest/develop/clients/redis-py/produsage/).

Если стенд использует Docker, выполнить на его хосте (имя контейнера сначала уточнить):

```sh
docker ps -a --format '{{.Names}}\t{{.Status}}\t{{.Ports}}'
docker inspect gmart-redis --format 'restarts={{.RestartCount}} oom={{.State.OOMKilled}} started={{.State.StartedAt}}'
docker logs --timestamps --since 2026-09-10T05:10:00 --until 2026-09-10T05:25:00 gmart-redis
docker exec <agents-container> /app/.venv/bin/python -c "import os,redis; print(redis.Redis.from_url(os.environ['REDIS_URL']).ping())"
```

Сопоставлять время с учётом часовых поясов. PING подтверждает доступность в момент проверки, но не исключает более ранний обрыв. Для Kubernetes имя `gmart-redis` может быть Service, а не контейнером Docker.

## 2. Urban API: 404, два падения provision

В окружении указан `URBAN_API_URL=http://urban-api:8000`. Есть 11 сообщений об отсутствующем ресурсе: 3 предупреждения создания чата, 6 предупреждений определения проекта сценария и 2 ERROR provision (строки 186 и 317).

Стек подтверждает сбой чтения каталога сервисов. Текущий UrbanApiClient обращается к `/v1/scenarios/{id}` и `/v1/scenarios/{id}/service_types`; JsonApiHandler дописывает эти пути к base URL. Ответ имеет вид `{"detail":"Not Found"}`. MCP Urban при этом отвечает 200/202: это отдельный канал, его доступность не доказывает правильность REST-адреса.

Наиболее вероятна ошибка префикса REST API либо несовпадение версии маршрутов. Примеры проекта используют `/api` в base URL, но наличие этого префикса у внутреннего сервиса в файле лога не подтверждено.

Исправление: из сети agents проверить OpenAPI Urban API и расположение обоих маршрутов для доступного пользователю сценария. Если они расположены под `/api/v1/...`, заменить окружение на `URBAN_API_URL=http://urban-api:8000/api` и пересоздать agents с обновлённой конфигурацией. Если маршруты уже под `/v1`, проверять версию API, существование сценариев 845/1135 и доступ к ним. Не лечить 404 повторными попытками. Добавить в ошибку метод, HTTP-статус и путь запроса без токенов — сейчас записан только base URL.

Предупреждение `failed to create chat` здесь не доказывает отказ ChatStorage: создание чата сначала получает project_id через Urban API. Позже в этом же логе ChatStorage успешно сохраняет сообщения.

## 3. Модель: бюджет уходит на рассуждения

Строка 24: `think= was dropped (OPENAI_THINK_MODE=off)`. Это отключение передачи настройки адаптером, а не отключение рассуждений модели.

Есть 5 предупреждений `empty content with finish_reason=length`, 4 предупреждения невалидного JSON планов (3 orchestrator и 1 NormGraph) и 4 предупреждения `Empty scenario-data action`. Часть сообщений описывает разные уровни одного сбоя, их нельзя складывать как независимые неудачные запросы. В частности, 19:39:13 JSON оборван внутри строки, затем следующая попытка возвращает пустой content. В scenario_data наблюдаются исчерпание 2500/5000 выходных токенов и иные пустые действия; не все пустые действия сопровождаются доказанным finish_reason=length.

Исправление для используемого gpt-oss через совместимый сервер:

```dotenv
OPENAI_THINK_MODE=reasoning_effort
OPENAI_THINK_EFFORT=low
```

Проверить, что переменные действительно передаются процессу и что сервер принимает их. В текущем адаптере эти значения применяются к вызовам с `think=False`; нужно проверить все JSON-планировщики. `low` уменьшает рассуждения, а не гарантирует их отсутствие. Не подставлять `none`/`minimal` без проверки поддержки Harmony. При оставшемся finish_reason=length увеличить именно бюджет ответа `num_predict/max_tokens` ограниченно, сохранить JSON Schema и конечное число повторов. Увеличение контекстного окна само по себе не увеличивает бюджет ответа. Не превращать технический пустой ответ в фиктивное успешное уточнение пользователя.

Поведение адаптера подтверждено локальным кодом; общая документация сервера: [vLLM reasoning outputs](https://docs.vllm.ai/en/latest/features/reasoning_outputs/).

## 5. Вход: четыре invalid_grant

Строки 14, 15, 709, 710: auth-helper вернул 400, `invalid_grant`, `Invalid user credentials`. Это отказы конкретных попыток входа; неверный пароль, пользователь или realm нужно различать по настройкам и журналу провайдера авторизации. Они не объясняют Redis ConnectionError.

Исправление: проверить вход действующей учётной записью через тот же auth-helper/realm и корректность передаваемых полей. Показывать понятную ошибку входа без внутренних URL, не повторять автоматически неверные реквизиты и не менять обработку Redis ради устранения этих 400.

## 6. No config file found

Один WARNING при старте. Следом приложение логирует заполненные настройки и запускается. В контейнере конфигурация из environment допустима; отсутствие `.env` не равно отсутствию конфигурации.

Исправление: при штатном использовании environment заменить предупреждение на INFO и валидировать обязательные поля. В текущем loader результат поиска определяется изменением переменных, а не наличием файла, поэтому текст предупреждения может быть неточным. Не создавать `.env` исключительно для подавления сообщения.
