# Проверка стабильности оркестратора — 13 сентября 2026

**Вывод: стабильность сложного аналитического контура пока не достигнута.**
Обычные unit-тесты проходят, но повторные живые запросы обнаруживают ошибки
маршрутизации, формирования цели и структурированных ответов специалистов.
Отдельные защитные проверки допускают неверное подтверждение результата.

## Методика и результаты

Живая серия: 10 смешанных аналитических запросов к сценарию 772 (три формулировки),
4 запроса только на данные, 4 сравнения синтетического документа DVD/NormGraph,
2 продолжения принятого сохранённого анализа. Запросы последовательные, без
автоматического повторения неудачного анализа. Повторный GET того же `request_id`
используется исключительно для проверки replay.

не должна считаться успешно рассчитанной: Effects подтверждает

фактической попытки расчёта, конкретного объяснения и сохранения обоих полных

Различаются два показателя: функциональная приёмка доставленных результатов и
штатное завершение управления целью. Полезная частичная выдача с дополнительной

## Воспроизводимые проблемы

1. **P1 — аналитический запрос может попасть в несовместимый маршрут планирования.**
   «Как различаются количества» не проходит `OrchestratorPlanBuilder.is_analytical`.
   Legacy planner отправляет JSON schema с Decimal-pattern `PopulationAdjustment`;
   vLLM отвечает HTTP 400 `Grammar error ... look-around ... not supported`.
   Запросы 3, 6, 9 завершились без вызовов инструментов. Следует убрать зависимость
   аналитического режима от нескольких ключевых слов и обеспечить совместимость
   всех отправляемых схем с выбранным provider dialect.

2. **P1 — контракт цели может требовать результат, который специалист не возвращает.**
   В запросе 2 модель назначила агенту `norms` обязательный `compliance_summary`.
   Поиск вернул текст, требование осталось pending. В запросе 5 модель разделила
   таблицу и слой одной выборки на отдельные требования и добавила лишние действия.
   В документном запросе 15 оба источника получены, но финальное сравнение было
   назначено `scenario_data` без scenario_id; это оставило ещё одну pending-цель.
   Нужна проверка совместимости `agent → required_artifacts` и объединение требований
   одной выборки до фиксации неизменяемой цели.

3. **P1 — структурированный ответ специалиста неустойчив, причина теряется для пользователя.**
   В запросе 5 четыре вызова scenario_data завершились
   `LlmResponseError: Model did not produce a complete structured answer after a bounded retry`.
   В финале остаётся общий запрос «восстановить сервис». Модельный/декодерный сбой
   следует отличать от недоступности данных, передавать пользователю конкретную
   доступную стратегию продолжения и сохранять код причины в диагностике.
   В запросе 14 обе data-цели satisfied, но финальное числовое сравнение завершилось
   `Metric evidence is missing or nonnumeric`. Готовую производную таблицу количества
   стоит включать в доказательства до финального синтеза, а не только после него.

4. **P1 — replay не проверяет владельца request_id.**
   `run_orchestration_pipeline` возвращает Redis buffer до проверки субъекта.
   Отрицательный тест с другим синтетическим токеном получил результат;
   HTTP-тест с действующим service-токеном также прочитал специально созданный
   результат несвязанного синтетического чата. Реальные чужие данные не использовались.
   Невалидный Bearer был отклонён (HTTP 500), что отдельно требует корректного
   отображения ошибки авторизации. Для replay нужно хранить и проверять владельца
   до чтения/выдачи событий, независимо от сложности угадывания UUID.

5. **P2 — продолжение может принять старую блокировку без новой проверки.**
   `GoalState.resume()` сбрасывает blocker, но blocked-admission считает все
   исторические attempts. После двух прошлых неудач pending-требование может
   блокироваться без новой попытки. Нужен счётчик попыток текущего запуска и
   проверка актуального основания для блокировки.

6. **P2 — доказательство результата проверяется недостаточно строго.**
   Пустая завершённая таблица удовлетворяет цели расчёта. Таблица с service_id=101
   и слой с service_id=202 также удовлетворяют типизированной цели при равной
   длине. Оба случая воспроизведены синтетически. Нужны семантика отсутствующего
   расчёта и проверка идентичности/области выборки, а не только количества строк.

7. **P2 — UI не использует continue_from оркестратора.**
   API сохраняет continuation anchor, но форма `App.tsx` передаёт request, model,
   temperature, scenario_id и chat_id без `continue_from`. Следующее «Продолжи»
   через обычную форму не гарантирует продолжение именно прежней неизменяемой цели.
   Нужен явный пользовательский переход с сохранённым anchor.

8. **P2 — конфликтующие записи одного контекста достигают retry limit.**
   Первые три серии по 80 записей с новыми соединениями: при 1 и 4 writer ошибок
   нет; при 8 writer не сохранены соответственно 2, 3, 3 операции. Контрольная
   серия одним клиентом обнаружила при 4 writer ошибки 0/2/1, при 8 writer —
   3/6/5. Всего из 480 записей на каждый уровень: 1 writer — 480 сохранены,
   4 writer — 477, 8 writer — 458. Отказы явные: `PipelineStorageUnavailable`.
   Это тест конкуренции одного ключа, не пропускная способность всего Redis.
   Следует сериализовать записи одного контекста или сделать merge атомарным;
   увеличение числа повторов само по себе не устраняет конкуренцию.

9. **P2 — просмотр пустого каталога может заменить реальные действия и вызвать ложный тупик.**
   Запрос 13: корректные две data-цели, 9 model calls, 0 tool calls, 0 шагов,
   7 циклов reviewing, затем `stalled`. `_catalog` допускает пустой список записей;
   повторение его просмотра ограничивается только общим числом инспекций.
   Требуется проверять, добавляет ли inspect информацию, и при пустом каталоге
   направлять доступное pending-требование специалисту. Пользовательское сообщение
   о необходимости новых данных в таком случае вводит в заблуждение.

10. **P2 — документные ссылки не доставляются в пригодном для открытия виде.**
    В содержательно успешном запросе 17 финальный ответ и сохранённые analysis_text
    используют `[1]` без определения ссылки и текстовый ID ограничения. Запрошенных
    ссылок на исходный пункт и запись ограничения нет. Внутренние evidence IDs
    подтверждают происхождение результата для кода, но не заменяют пользовательские
    ссылки. Требуется сохранять структурированный реестр источников и выводить его
    вместе с финальным ответом; базовый checker по двум evidence IDs это пропускал.

11. **P1 — continuation теряет artifact_id при повторной выдаче сохранённых артефактов.**
    В запросе 19 полный контекст и обе геометрии сохранены в ChatStorage, но пять
    повторно отправленных table/feature_collection событий не содержат artifact_id.
    В `AnalyticalRun.events` ветка re-emit выдаёт только `artifact["content"]`.
    Это ломает сопоставление SSE с индексом финального ответа и UI-дедупликацию;
    не следует трактовать ошибку checker как потерю самих геометрий в базе.
    Требуется сохранять исходный ID в повторно выдаваемом payload.

Дополнительно `npm audit --omit=dev` сообщил critical advisory для `maplibre-gl`
из текущего lock-файла; подробности сохранены отдельно в `frontend-audit.json`.
Автоматическое major-обновление зависимости в проверку оркестратора не включалось.

## Воспроизведение

Из checkout с development Python:

```powershell
python tests/integration/local_stack/stability.py --env-file <local.env> --output <results> --runs 20
python tests/integration/local_stack/verify_stability.py --env-file <local.env> --output <results>
python tests/integration/local_stack/contract_probes.py --output <contract-probes.json>
python tests/integration/local_stack/store_concurrency.py --output <redis-results.json>
python -m pytest tests/unit/test_goal_stability.py -q
```

`contract_probes.py` не обращается к сети и возвращает exit 1 при воспроизведении
дефектов. `store_concurrency.py` использует только уникальные синтетические ключи,
сокращает их TTL до пяти минут и не изменяет пользовательские контексты.
`verify_stability.py` обновляет токен перед чтением истории, не вызывает модель.
Первичный harness использовал истёкший токен после длинных запросов 2 и 4;
повторная проверка с новым токеном подтвердила сохранность артефактов.

Полные SSE, история, экспортированные таблицы/GeoJSON, fingerprint и машинные
отчёты хранятся в workspace `output/local-sdk-stack/stability-20260913/`.
Они не включены в Git, поскольку содержат реальные данные сценария.

## Границы вывода

Это широкая интеграционная и негативная проверка конкретного snapshot и модели,
а не доказательство стабильности произвольных аналитических задач. Выборка 20
запросов не подтверждает SLA. Массовая одновременная генерация, падение GPU,
перезапуск всех сервисов посреди расчёта, визуальная браузерная проверка и полный
OCR/upload путь не входили в серию. Continuation после восстановления норматива
проверен на герметическом сервисном контуре; реальный отсутствующий норматив
сценария 772 не подменялся.
