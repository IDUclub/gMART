# Исправления на стороне gMART после анализа develop-лога

Внесены в рабочую копию 10 сентября 2026. Значение и маршруты `URBAN_API_URL` не менялись: адрес исправляет владелец стенда. Образ на develop этой работой не обновлялся.

## Что изменилось

- Redis-клиент проверяет соединение перед командой после 30 секунд простоя; connect/read timeout — 5 секунд, TCP keepalive включён. Глобальные повторы команд явно отключены, чтобы не повторять неидемпотентные операции общего клиента.
- PipelineStateStore делает до трёх попыток для безопасно повторяемых операций, с паузами 0,1 и 0,2 секунды. Постоянная недоступность возвращает классифицированную ошибку хранилища (HTTP 503 для обычного REST; событие error для уже открытого SSE). Ошибка аутентификации Redis не повторяется.
- События сохраняются перед отправкой SSE. Убраны бесконтрольные фоновые `create_task(buffer_event(...))` у всех шести предметных процессов и оркестратора, включая внутренние сценарные процессы. Ошибка сохранения больше не теряется в `Task exception was never retrieved`.
- Буфер записывается транзакцией WATCH/MULTI/EXEC вместе с маркером уникального события и TTL. Потеря подтверждения после записи не создаёт дубль при повторе. Два разных события с одинаковым текстом сохраняются оба. Формат выдачи/replay остался прежним. Добавляется внутренний ключ `pipeline:<request_id>:event_ids` с тем же TTL.
- Блокировка чата учитывает владельца атомарно. Повтор успешного захвата с тем же request_id считается успешным; освобождение не удаляет блокировку другого запроса.
- SSE-обёртка сообщает об ошибке хранилища без повторного запуска всего расчёта. Постоянный отказ Redis не превращается в успешный результат. Сохранение до отправки добавляет зависимость скорости SSE от задержки Redis; это осознанное изменение по сравнению с отправкой до подтверждения записи.
- Для gpt-oss вызовы с think=False получают поддерживаемый reasoning_effort (low вместо неподдерживаемых none/minimal), в том числе при старом OPENAI_THINK_MODE=off. Явные поддерживаемые значения сохраняются. Для других моделей поведение выбранного режима сохраняется.
- Пустой или обрезанный ответ структурированного LLM-вызова повторяется один раз с увеличенным выходным бюджетом. Повтор имеет потолок 8192 токена для автоматически увеличиваемого бюджета; больший исходный бюджет не урезается. Неуспех после повтора возвращает техническую ошибку, а не выдуманное уточнение пользователя. Это относится к нестриминговому JSON; частично отправленные свободные ответы автоматически заново не генерируются.
- Настройка reasoning по умолчанию в deployment compose и примере окружения изменена на low. Убрана категоричная диагностика, объявлявшая любой пустой ответ следствием low: нужно учитывать реальную причину завершения и бюджет.
- Подтверждено ранее внесённое исправление передачи выбранного scenario_id в планировщик и отделения истории от текущего запроса.
- `/auth/token` возвращает понятный 401 для invalid_grant без внутренних адресов/ответа auth-helper. Ошибки настройки или доступности helper отображаются отдельно как 502 и не выдаются за неверный пароль. Настоящие неверные реквизиты код исправить не может — потребуется корректная учётная запись/realm.
- Наличие `.env` определяется фактом нахождения файла, даже если переменные не изменились. Явное окружение процесса имеет приоритет перед `.env`; устранены неправильные имена `.env.src.agents.*`. Если файл не найден, штатная загрузка из environment логируется как INFO. Значения URL в файлах не переписывались.

## Проверка

1. Десять новых регрессионных тестов; первые восемь воспроизвели проблемы до исправления и прошли после.
2. Полный Windows unit-набор: **733 passed**. Linux-зависимые workspace_store: **4 passed** в одноразовом контейнере.
3. Изолированный настоящий Redis 7: **3 passed** — сервер закрывает соединение тестового клиента, потеря подтверждения реально выполненной транзакции, повтор/освобождение блокировки. Рабочий Redis не отключался. Тестовые ключи удаляются адресно, FLUSHDB/FLUSHALL не используется.
4. Удалённый local-gpu/gpt-oss-20b: первый JSON с бюджетом 16 токенов получил finish_reason=length; единственный повтор с 4096 токенами и low вернул полный `{"ok":true}`.
5. Два запроса из лога с scenario_id=845 — о землях водяного фонда и населении — получили план execute → scenario_data без лишнего уточнения. Это проверка планирования, не наличия требуемых данных в Urban API.
6. Frontend: **20 passed**.

Воспроизводимая проверка Redis выполняется файлом `tests/integration/test_redis_resilience.py`. Нужно явно задать `GMART_TEST_REDIS_URL` на отдельный тестовый Redis. Остальные проверки находятся в `tests/unit/test_develop_log_regressions.py` и существующих тестах оркестратора.

## Применение на develop

Собрать и обновить **образ agents из текущего кода**. Обновления файлов на рабочей машине недостаточно для изменения уже запущенного контейнера. Сохранить корректные сервисные настройки и самостоятельно исправить Urban API URL.

Для gpt-oss рекомендуемое окружение процесса:

```dotenv
OPENAI_THINK_MODE=reasoning_effort
OPENAI_THINK_EFFORT=low
```

Значения из GitHub environment / окружения запуска имеют приоритет над compose defaults. Не публиковать REDIS_URL с паролем в логах или командах диагностики. Если после обновления соединения всё равно постоянно обрываются, клиент вернёт явную ошибку; восстановление упавшего Redis, исправление DNS/сети или реквизитов подключения остаётся задачей инфраструктуры.
