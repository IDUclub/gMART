# Document-QA agent (RAG по нормативной документации)

Агент `document-qa` отвечает на вопросы по **нормативной документации** (градостроительство и
городское планирование): извлекает фрагменты из **IDU_DVD** (векторная БД документов, через MCP
по `DVD_MCP_SERVER`) и формирует ответ, обоснованный источниками.

Тестовый UI также позволяет пользователю загрузить собственный документ в индекс проекта.
REST-адрес IDU_DVD задаётся через `DVD_API_URL`; если переменная отсутствует, gMART выводит его
из `DVD_MCP_SERVER`, удаляя завершающий `/mcp`.

Общие механики — авторизация (`Authorization: Bearer <token>`), формат SSE, переподключение по
`request_id` — те же, что в [frontend-service.md](frontend-service.md). Ниже только специфика
этого агента.

> **`GET /documents/qa/stream` — публичный.** Вопрос по общей нормативной базе отвечается без
> `Authorization`: см. [Публичный доступ](#публичный-доступ).

## Пользовательские документы

- `POST /documents/user-documents` — multipart upload. Поля: `file`, необязательные `name`,
  `version`, `project_id`, `scenario_id`; требуется хотя бы `project_id` или `scenario_id`.
  Если передан только сценарий, gMART получает проект через Urban API.
- `GET /documents/user-documents?scenario_id=...&project_id=...` — список документов текущего
  пользователя в выбранном проекте.
- `PATCH /documents/user-documents/{name}` — multipart-обновление существующего документа.
  Поля: `file`, необязательные `version`, `project_id`, `scenario_id`; ответ `202` содержит новый
  `job_id`, прогресс которого читается тем же SSE-методом.
- `DELETE /documents/user-documents/{name}?scenario_id=...&project_id=...` — удаление документа и
  всех его версий. Необязательный `version` ограничивает удаление одной версией.
- `GET /documents/user-documents/jobs/{job_id}/stream` — SSE-снимки прогресса загрузки и
  индексации. Поток завершается при `status=done` или `status=error`.

Ответ upload содержит `job_id`. Клиент сначала показывает сетевую передачу multipart-файла
как этап 0–10%, затем подключается к SSE. Снимок содержит `stage`, `phase`,
`stage_index` / `stage_total`, `task_progress` для текущего этапа и `overall_progress` для всего
пайплайна. Этапы IDU_DVD: `structure-markup`, `type-tagging`, `hierarchy`, `identity`,
`references`, `embeddings`, `indexing`.

gMART не пересылает пользовательский bearer-token в IDU_DVD напрямую: вызов выполняется с
service-token и заголовком `X-User-Id`, извлечённым из уже проверенного JWT. При запросе
`GET /documents/qa/stream?...&scenario_id=...` тот же `scenario_id` передаётся в MCP
`search_texts` / `search_tables` / `search_all`; поэтому поиск объединяет общую нормативную базу
и пользовательский индекс проекта. Без `scenario_id` агент продолжает работать только по общей базе,
и в этом случае токен не требуется вовсе — у анонимного вызова просто нет `X-User-Id`.

## Контекст диалога

Для каждого запроса с `chat_id` агент читает `/api/v1/chat_context/{chat_id}`:
опубликованную сводку и ещё не вошедшие в неё сообщения. Последние сообщения
сохраняются дословно для выбора вариантов. При недоступности summary используется
история чата. Свежий вопрос имеет приоритет над сводкой; summary помогает выбрать
документ и понять вопрос, а нормативные сведения берутся из IDU_DVD.
После сохранения ответа ставится задача обновления summary (`documents-v1`).
`context_worker` обрабатывает её асинхронно и запускается вместе с сервисами.

Выбор `Вариант 2: Раздел 3. Термины и определения` продолжает исходный вопрос.
Запрос «Что написано…» возвращает полный найденный текст без пересказа, если
пользователь дополнительно не просит объяснения. Критик проверяет существенные
ошибки, условия и ссылки, не требует необязательных подробностей и изменения стиля.
Терминальное событие `error` показывается как ответ с сообщением сервера.

## Как работает

Перед поиском **context_check** проверяет сохранённые исходные тексты последнего
обращения к IDU_DVD. Они хранятся отдельно от summary и черновиков ответа в состоянии
чата, с областью сценария и сроком жизни `PIPELINE_TTL`. Доступ к чату проверяется
через ChatStorage. Последняя полная цитата также может восстановить источники из
истории старого чата. Обычные ответы модели и summary источниками норм не становятся.

- Если текстов достаточно, модель отвечает по ним и проходит `self_review`, без
  нового обращения к IDU_DVD. Например, после выбора раздела «расскажи вкратце
  об этом пункте» означает краткое объяснение выбранного раздела.
- Если не хватает данных, выполняется поиск ниже. Новый документ, редакция,
  сценарий или просьба обновить сведения требуют проверки области/нового поиска.
- Если предмет неоднозначен, используются те же уникальные варианты по структуре
  документ → раздел → пункт. Незавершённое уточнение обрабатывается раньше ответа
  из памяти; выбор варианта продолжает исходный вопрос.

Итеративный цикл (до 3 итераций):

1. **retrieval_planning** — LLM подбирает параметры поиска: запрос, тип (`text` / `table` / `all`),
   число фрагментов и ширину соседнего контекста. Поисковый запрос — тема требований, а не
   действие: глаголы запроса и слова «документы, содержащие…» удаляются детерминированно.
   Для семантического поиска планировщик добавляет до двух альтернативных формулировок темы;
   теги корпуса IDU_DVD используются как фильтр, только если они есть в корпусе.
   Вопрос «какие документы / регламенты…» получает тип `document_list`.
2. **searching** — детерминированный поиск в IDU_DVD по выбранным параметрам. Результаты
   альтернативных формулировок объединяются без дублей. Для `document_list` затем ищется
   текст документов, упомянутых в найденных фрагментах, и дополнительные фрагменты найденных
   документов (`search_filtered` с `document_names`). Каждый поиск логируется: документ,
   редакция, номер, score — без текста фрагментов.
3. Для запроса исходного текста возвращается полная цитата. Для объяснений **answer_drafting** — сервис собирает черновик внутри пайплайна. При достижении границы генерации
   продолжает ответ с проверяемым перекрытием последнего фрагмента.
4. **self_review** — критик-LLM проверяет черновик по найденным фрагментам. Если ответ не устроил —
   ответ переписывается с учётом замечаний. Планировщик вызывается только в первом раунде
   и после пустого поиска; в остальных раундах план прошлого раунда используется повторно,
   а поиск меняют только предложенный критиком запрос (с сохранением фильтров) или расширение.
   Повторный план использует уже найденные источники и подготовленный контекст, без повторного
   MCP-вызова и события `tool_call`. По одним и тем же фрагментам пишется не более двух
   черновиков (ответ и одна переписка, `DVD_MAX_DRAFTS_PER_RETRIEVAL`); третий раунд возможен
   только с новым поиском. Запросы альтернативных формулировок и поиск по документам идут параллельно.
   Если отказ вызван нехваткой сведений, тот же поиск не повторяется: он расширяется
   (20 фрагментов, `kind=all`, соседний контекст +1, без тегов), а если расширять нечего,
   цикл сразу завершается частичным ответом без нового черновика. Черновик пишется с
   температурой не выше `DVD_ANSWER_TEMPERATURE` (0.2), без таблиц: если модель всё же вернула
   Markdown-таблицу, до проверки критиком она переписывается в список, строка на строку. Строки разметки
   (шапки и разделители таблиц, заголовки) не проверяются как утверждения; доказательства
   критика ссылаются только на метки `[N]`.
   Кеш действует только внутри одного выполнения запроса. Отклонённые черновики не отправляются
   клиенту. После третьего отказа возможен частичный ответ из проверенных цитат источников.

Через `/orchestrator` агент получает исходный вопрос пользователя; формулировка задачи
маршрутизатора передаётся как уточнение, а результаты предыдущих шагов — как контекст диалога.
Поэтому обозначения документов из ответа предыдущего агента не становятся фильтрами поиска.
Поисковый запрос строится по теме задачи: если планировщик повторил вопрос вместе с задачей,
остаётся только тема задачи, чтобы части вопроса для других агентов (например, обеспеченность)
не попадали в векторный поиск. Вид вопроса (`document_list`) определяется по словам
пользователя, а не по формулировке задачи.

Документ, названный только в сводке чата (например, процитированный прошлым ответом),
ограничивает поиск лишь для продолжения по адресу или местоимению («а пункт 3.3?», «что в нём
про…»). Новый вопрос в том же чате ищется по всей базе. Документ, явно выбранный пользователем,
сохраняется как раньше.
Обзорный вопрос о регламентах, нормативах или ограничениях для вида объекта («какие есть
регламенты застройки школ») оркестратор выполняет двумя шагами: `norms`, затем `documents`.
План только из шагов `norms` и `documents` выполняется параллельно: все шаги стартуют сразу,
а события отдаются по шагам в порядке плана. Такие шаги не получают выжимку предыдущих.

Если шаг плана оркестратора завершился ошибкой (`status: "failed"`), остальные шаги всё равно
выполняются: агенты получают данные сценария сами. Вместо результата упавшего шага следующие
получают пометку, что его нет, и не подставляют значения вместо него. Статус `skipped` остаётся
только за шагами после уточнения (`needs_clarification`) или приостановки.

Геометрии в этом пайплайне нет — событие `feature_collection` агент не присылает.

## Эндпоинты

### `GET /documents/qa/stream` — SSE

```http
Authorization: Bearer <access_token>   # необязательно, см. «Публичный доступ»
```

| Параметр | Тип | По умолч. | Описание |
| --- | --- | --- | --- |
| `request` | `string` | обязательный | Вопрос пользователя. |
| `model` | `string` | `gpt-oss:20b` | Имя модели Ollama. |
| `temperature` | `number` | `1.0` | Температура генерации. |
| `scenario_id` | `number \| null` | `null` | ID сценария Urban API. Если `chat_id` не передан — создаётся чат с этим `scenario_id` и выведенным из него `project_id`. **Требует авторизации.** |
| `chat_id` | `string \| null` | `null` | UUID чата из Chat Storage для продолжения диалога. **Требует авторизации.** |
| `request_id` | `string \| null` | `null` | UUID пайплайна для переподключения после разрыва. |

#### Публичный доступ

`GET /documents/qa/stream` — единственный эндпоинт агента, работающий без `Authorization`.
Анонимный запрос обслуживается только в публичном контуре:

- поиск идёт **по общей нормативной базе**; пользовательский индекс проекта недоступен;
- история не ведётся: чат в Chat Storage не создаётся, события `chat_created` не будет,
  вопрос и ответ не сохраняются (Chat Storage принимает вызовы только с пользовательским JWT);
- переподключение по `request_id` работает — буфер событий лежит в Redis, а не в Chat Storage.

Вызов в IDU_DVD остаётся авторизованным и в этом случае: он идёт с тем же service-token, а в
`X-User-Id` (заголовок обязателен для поисковых инструментов IDU_DVD) подставляется
`anonymous` — значение учитывается только вместе с `project_id`/`scenario_id`, которых у
анонимного запроса быть не может.

Всё, что привязано к пользователю, требует токена. Анонимный запрос с `scenario_id` или
`chat_id` — а также переподключение к пайплайну, запущенному с одним из них, — отклоняется
с `401`; параметры **не** отбрасываются молча, чтобы фронт не получил ответ по более узкой
базе, чем запрашивал.

С заголовком `Authorization` поведение эндпоинта прежнее.

### `POST /documents/a2a` — A2A JSON-RPC

Карточка агента: `GET /documents/.well-known/agent-card.json` (имя `document-qa-agent`).
Методы: `SendMessage`, `SendStreamingMessage`, `GetTask`, `ListTasks`, `CancelTask`,
`GetExtendedAgentCard`. `scenario_id` / `chat_id` передаются в `params.message.metadata`.

## Типы SSE-событий

Конверт стандартный (`{ "type", "content" }`). Набор событий этого агента:

| Тип | Назначение |
| --- | --- |
| `pipeline_started` | первое событие; сохранить `content.request_id`. |
| `status` | прогресс; `content.status` ∈ `context_check`, `retrieval_planning`, `searching`, `answer_drafting`, `self_review`, `finalizing`. |
| `chunk` | текст ответа; `content = { text, done, iteration }`. |
| `tool_call` | вызов поиска в IDU_DVD (`content.mcp_source = "DVD_MCP_URL"`). |
| `service_event` | создан чат (`chat_created` с `chat_id` / `chat_title`). |
| `warning` | неблокирующее предупреждение (см. ниже). |
| `error` | ошибка запроса. Завершите ожидание и не считайте ответ успешным. При исчерпании повторов генерации пайплайн получает `failed`, без успешного `done: true`. |

> Этот агент **не** использует `feature_collection`, `token_expired`, `pipeline_suspended`:
> обновление токена не применяется (IDU_DVD MCP без авторизации; токен нужен только для истории
> в Chat Storage).

### `chunk` — проверенный ответ

```json
{ "type": "chunk", "content": { "text": "Согласно [1]…", "done": false, "iteration": 2 } }
```

Текст нового ответа поступает после `self_review`; отклонённые черновики и незаконченные
продолжения не отправляются. `iteration` обозначает принятую итерацию. Завершение подтверждается
чанком с `done: true`. Сохраняйте поддержку группировки по `iteration` для воспроизведения
ранее сохранённых потоков. До получения текста показывайте прогресс по событиям `status`.

### Бюджет генерации

Каждый вызов получает весь остаток контекстного окна после инструкций, истории,
источников и сообщений продолжения. Отдельного потолка выхода нет. Размер входа
на vLLM считается его токенизатором; если он недоступен, используется консервативная
оценка по байтам UTF-8. Подробности — в разделе «Размер запроса к модели».

`DVD_ANSWER_RETRIES` (2; допустимо 0–4) ограничивает дополнительные попытки одного черновика.
При `length`/`max_tokens` сохраняется видимый текст, а скрытые рассуждения начинаются
заново. Для продолжения пересчитывается свободное место в том же окне. Последний
незавершённый фрагмент повторяется и проверяется перед объединением. Весь результат
проверяется критиком. Ошибки фильтрации и поток без подтверждённого завершения
не считаются успешным ответом.

### `warning`

```json
{
  "type": "warning",
  "content": {
    "code": "project_id_unavailable",
    "scenario_id": 772,
    "message": "Не удалось получить идентификатор проекта (project_id) по scenario_id=772. Фильтр проекта не будет сохранён, выполнение запроса продолжается."
  }
}
```

Сейчас единственный код — `project_id_unavailable`. Чат всё равно создаётся (только с `scenario_id`),
выполнение запроса продолжается. Покажите ненавязчивое уведомление.

### `self_review` — самопроверка

Если после ограниченных повторных попыток не удалось обработать часть источников,
агент продолжает работу по доступным фрагментам. Итоговый ответ проходит самопроверку
и содержит явное предупреждение о неполноте; предупреждение сохраняется в истории
и при повторном подключении. Если пригодных фрагментов не осталось, запрос завершается
контролируемым событием `error`, без неподтверждённого ответа.
При исчерпании бюджета генерации обработка повторяется на меньших частях исходного
текста; в диагностике сохраняется причина `output_truncated`.

Отдельное приветствие («Привет», «Здравствуйте», «Добрый день») получает короткий
ответ без поиска по документам и проверки цитат. Приветствие вместе с вопросом
проходит обычный поиск и самопроверку.

Статус `self_review` с текстом «Уточняю ответ по источникам…» означает, что начинается
исправление черновика. Замечания критика, включая последнее, сохраняются только в серверном
журнале с `request_id`, номером итерации и причиной. Исчерпание проверок (`review_exhausted`)
и невалидный ответ критика (`critic_invalid_response`) различаются в журнале, но не раскрываются
в SSE. Невалидная проверка не запускает новый поиск: она завершает запрос как технический сбой.
После `review_exhausted` сервис собирает подтверждённые утверждения всех трёх попыток.
Критик для каждого утверждения указывает `supported`, `contradicted` или `insufficient`
и дословные цитаты с метками источников. Схема ответа ограничивает формулировки списком
строк черновика, чтобы критик не подменял проверяемое утверждение текстом источника.
Утверждение должно присутствовать в черновике,
а его цитаты — в соответствующих исходных фрагментах; отсутствие замечаний не считается
подтверждением. Сведения и цитаты сохраняются в чекпоинте для продолжения после прерывания.

Если есть кандидаты, отдельная финальная проверка выбирает только их идентификаторы:
проверяет обоснованность и совместимость сведений из разных попыток. Неустранённые
противоречия и неполные утверждения исключаются. Новая генерация текста ответа не выполняется:
сервер выводит только дословные цитаты, заново нумеруя ссылки и сохраняя исходные реквизиты.
Пересказы из отклонённых черновиков не выводятся даже при одобрении моделью: живая проверка
показала, что критик может пропустить потерю условий или области применения нормы.
Ответ начинается с «По найденным источникам удалось подтвердить следующее…» и явно помечен
как частичный. Если подтвердить ничего нельзя, возвращается «Не удалось подтвердить ответ
по найденным фрагментам.» и перечень документов и номеров фрагментов, которые нашёл поиск,
плюс документы, упомянутые в них (только метаданные поиска, без пересказа требований).
Для `document_list` этот перечень добавляется и к частичному ответу. Оба результата заканчиваются `done: true`, сохраняются в истории
и могут быть воспроизведены при переподключении. Технический сбой проверки по-прежнему
завершается событием `error`, а не частичным ответом.

Пользователю при терминальном сбое остаётся общее сообщение «Не удалось завершить запрос.
Повторите попытку.» и пустой `traceback`. Отклонённый черновик не выдаётся как успешный ответ.

## Переподключение и история

Механика `request_id` (буфер событий + резюм с последнего чекпоинта) и `chat_id` — как в
[frontend-service.md](frontend-service.md) (флоу 1, 2, 4). Окно переподключения — 360 секунд
(`PIPELINE_TTL`); после истечения состояние в Redis удаляется и запрос с тем же `request_id`
стартует заново.

## Выбор области и способа поиска

Агент сначала заполняет ограничения из вопроса и контекста: документ, редакцию,
структурный адрес, принадлежность пользовательскому проекту. Выбранный документ
сохраняется в состоянии чата после уточнений и ответов. Новый номер пункта заменяет
адрес внутри этого документа: «СП 55, пункт 3» → «Есть в СП пункт 3.3?».
Явно другой документ или «по всей базе» меняет область поиска.

Точный пункт/полная цитата извлекаются целиком. Для темы внутри документа или раздела
вызывается DVD `search_filtered`: сначала разрешение фильтров, затем векторное ранжирование
внутри области. `rank_by_relevance` отличает вопрос по теме раздела от запроса полного текста.
Поиск только по теме без выбранного документа использует обычный векторный поиск.
«В моём документе» исключает общий корпус; требуется выбранный сценарий проекта.

Уточнение показывает документ и редакцию, затем вложенные разделы с названиями и
нумерованные варианты пунктов. Родительские сущности не повторяются. Выбор варианта
сохраняет исходный вопрос и фильтры. Разные структурные элементы с одинаковыми номерами
не объединяются по одному совпадению подписи. Пустой результат не расширяет область.

Для совместимого обновления сначала разверните DVD с MCP `search_filtered`.

### Размер запроса к модели

Контекстное окно каждого вызова — `DVD_CONTEXT_WINDOW_TOKENS` (по умолчанию **100 000
токенов**), но не больше `max_model_len` сервера модели; если сервер его не сообщает, окно
не превышает 32 000. В него входят входные сообщения (инструкции, история и источники),
служебное оформление и резерв генерации (рассуждения и ответ). Это не перенастраивает сервер
модели: чтобы окно действительно выросло до 100 000, vLLM должен быть запущен с
`--max-model-len` не меньше этого значения.

Нужно ли сжимать найденные фрагменты, решается по числу токенов модели (серверный
`/tokenize`), а не по размеру в байтах: кириллица занимает около 7 байт на токен, и
сравнение байтов с бюджетом в токенах запускало сжатие для контекста, который помещался
в окно. Фрагменты, помещающиеся в окно, передаются модели без изменений.
Отдельного ограничения по символам нет; прежний `DVD_REQUEST_MAX_CHARS` больше не используется.

Планировщик, выжимка источников, проверка и итоговый ответ получают **весь остаток окна**
после входного контекста, включая место для рассуждений. Отдельных потолков на выход нет:
`DVD_PLANNER_MAX_TOKENS`, `DVD_SUMMARY_MAX_TOKENS`, `DVD_REVIEW_MAX_TOKENS`,
`DVD_ANSWER_MIN_TOKENS` и `DVD_ANSWER_MAX_TOKENS` не используются.

На vLLM размер входа вычисляется серверным `/tokenize` с шаблоном чата выбранной модели.
Из окна вычитаются полученное число токенов и технический запас 256 токенов на оформление.
Если токенизатор недоступен, используется консервативная оценка по байтам UTF-8.
Источники предварительно сокращаются с резервом под генерацию; это не потолок выхода.
Большие источники обрабатываются частями. Инструкции и история не обрезаются молча.
Если общий контекст не помещается в окно, запрос не отправляется модели.
