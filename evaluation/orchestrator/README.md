# Проверка оркестратора

`queries.md` содержит 200 запросов на русском языке. `cases.json` — тот же набор
с ожидаемыми маршрутами, контекстом, доступностью агентов и критериями ответа.
`build_cases.py` воспроизводит набор без обращения к LLM.

Дополнительно `mixed_queries.md` / `mixed_cases.json` содержат **100 составных
запросов**, воспроизводимых через `build_mixed.py`: 20 сочетаний двух агентов,
20 сочетаний трёх, 20 сложных продолжений диалога, 15 сравнений/форматов данных,
15 конфликтов/ограничений возможностей и 10 случаев нехватки контекста. Это
отдельный набор сверх исходных 200, а не замена 20 простых mixed-примеров.

Охват: restriction, **compliance**, provision, scenario_data, documents, norms —
по 25 запросов; 20 составных запросов; 15 продолжений диалога; 15 пограничных
случаев. Compliance существовал как отдельный API-процесс, но отсутствовал в
каталоге оркестратора. Он добавлен с вызовом `run_compliance_pipeline` и передачей
NormGraph. `/llm` — прямой доступ к модели, а Synapse — отдельный внешний
оркестратор, поэтому они не используются как предметные исполнители этого каталога.

160 запросов использованы для диагностики. Каждый пятый запрос (40 штук) отложен
для итоговой проверки; его результаты не использовались для изменения промпта.
Это небольшой искусственный набор похожих тематик, а не независимая выборка
реального пользовательского трафика. Один прогон при temperature=0 не оценивает
стабильность модели между повторениями.

## Что измеряет автоматическая оценка

`run_planner.py` вызывает **настоящий** `OrchestratorPlanBuilder` и удалённую LLM
из graphify `local-gpu`/`local_gpu`. Подставных ответов модели нет. Проверяются
режим, точный набор агентов, отсутствие повторных шагов одного агента, наличие
вопроса при уточнении и сохранение выбранных деталей 15 продолжений диалога.
Порядок шагов, все параметры задач и достоверность конечного ответа этой метрикой
не проверяются. В артефактах сохраняются планы, ошибки, задержки, хеш исходников
и хеш набора. Состояние каталогов задаётся явно: этот этап не проверяет доступность MCP.

Один заведомо спорный эталон: `orch-123` ссылается на «найденный пункт», но не
содержит истории. В исходном наборе ожидается documents; уточняющий вопрос здесь
тоже обоснован. Исходная разметка сохранена для сопоставимости, а это ограничение
необходимо учитывать при интерпретации процента. Не следует подгонять маршрутизатор
под ответы такого эталона.

```powershell
.venv/Scripts/python.exe evaluation/orchestrator/build_cases.py
.venv/Scripts/python.exe evaluation/orchestrator/run_planner.py --out benchmarks/data/orchestrator_new --concurrency 8
```

## Полная проверка конечных ответов

`run_live.py` запускает актуальный код сервисов локально, вызывает реальные
локальные IDU MCP (`8002`), Effects (`8080`), DVD (`8100`), NormGraph (`8020`),
настроенный Urban MCP/REST и выбранную LLM. История тестового диалога передаётся
планировщику из набора, ChatStorage отключён; состояние изолировано в fakeredis.
Это проверка сервисного процесса, а не тест развёрнутого HTTP-контейнера/UI.

Скрипт рассчитан на уже настроенный локальный OIDC bridge (`8085`) данного стенда.
Он использует локальные идентификаторы gmart/gmart-internal; реальные пароли
пользователя остаются в конфигурации bridge. Для другого стенда транспортную
конфигурацию нужно адаптировать. Секреты не записываются в набор запросов.

```powershell
.venv/Scripts/python.exe evaluation/orchestrator/run_live.py --out benchmarks/data/orchestrator_live --concurrency 4 --timeout 240
```

Сначала стоит выполнить по одному запросу каждого направления (`--ids orch-001
orch-026 orch-051 orch-076 orch-101 orch-126`). Для возобновления предусмотрен
`--resume`: скрипт отказывается смешивать исходники с разными хешами.

События `completed` сами по себе не подтверждают точность. У каждого результата
изначально `factual_verdict=not_reviewed`. Чтобы установить достоверность, нужно
сверить таблицы/ID/количества с REST Urban API, геометрию — с исходными слоями,
расчёты — с Effects, нормы и цитаты — с фактически полученными фрагментами
NormGraph/IDU_DVD. Отсутствие источников, технические ошибки и неверные ответы
учитываются раздельно. Пересылка результатов реальных сервисов удалённой модели
требует разрешения для этого стенда.

Для проведённого прогона пользователь разрешил отправлять эти результаты
на удалённую модель local-gpu. `review_answers.py` выполняет дополнительный
разбор обоснованности по трассам; поскольку судья использует ту же модель, его
оценки не являются независимой экспертной проверкой. `capture_reference.py`
сохраняет отдельные REST-снимки, `verify_geometry.py` пересчитывает геометрию
по сохранённым входам. `report.py` формирует сводку и поштучные результаты.

```powershell
.venv/Scripts/python.exe evaluation/orchestrator/build_mixed.py
.venv/Scripts/python.exe evaluation/orchestrator/run_live.py --cases evaluation/orchestrator/mixed_cases.json --out benchmarks/data/mixed_new --concurrency 6 --timeout 300 --document-context-window 65536
.venv/Scripts/python.exe evaluation/orchestrator/review_answers.py --cases evaluation/orchestrator/mixed_cases.json --runs benchmarks/data/mixed_new/runs --out benchmarks/data/mixed_new/reviews
.venv/Scripts/python.exe evaluation/orchestrator/verify_geometry.py --runs benchmarks/data/mixed_new/runs --out benchmarks/data/mixed_new/geometry.json
```

Консолидированный отчёт: `report.md`; подтверждённые ошибки и ограничения:
`findings.md`; поштучные результаты: `results.md`.

Для проверенного сервера local-gpu `/v1/models` подтвердил `max_model_len=65536`.
Полный mixed запущен с `--document-context-window 65536`; для запуска самого
API эквивалентная настройка — `DVD_CONTEXT_WINDOW_TOKENS=65536` в окружении
процесса. Она допустима только для модели с подтверждённым соответствующим окном.
Этот параметр уменьшает лишнее разбиение нормативных фрагментов; он не расширяет
контекст на сервере. Манифест сохраняет окно, таймаут и параллелизм.

Пробный разбор ответов через `review_answers.py` не оказался достаточно надёжным
для метрики точности: выбранная модель путала сокращённые примеры с полными
выдачами и предполагала отсутствующие источники. Эти оценки сохраняются как
диагностические сигналы, но не считаются подтверждёнными ошибками.

## Изменения поведения

- Выбранный `scenario_id` передаётся в контекст планирования.
- Завершённая история диалога отделена от текущего запроса.
- Добавлен маршрут compliance; описание restriction соответствует его геометрической роли.
- Используется структурированный JSON-ответ; пустые подзадачи отклоняются и исправляются.
- План длиннее трёх шагов вызывает уточнение вместо молчаливого обрезания.
- Уточнение подчинённого агента останавливает зависимые шаги и получает статус
  `needs_clarification` в SSE. `pipeline_failed` обрабатывается как ошибка.
- Черновик и таблицы неуспешного шага не сохраняются как подтверждённый итог.
- Интерфейс различает успех, неполное выполнение и уточнение.

Последние изменения не заменяют проверку фактической точности каждого предметного
агента. Между шагами по-прежнему передаётся текстовая выжимка до 1500 символов,
а не полный набор таблиц или геометрии. Лимит в 3 шага сохранён.
